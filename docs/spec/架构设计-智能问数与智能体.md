# 智能问数与智能体平台 · 架构设计文档

> **范围**：以《通用智能问数设计方案 v1》(10 个 Tool) 为底，叠加《智能体平台整合设计方案 v2》新增的 4 个 Tool 与 Skill/Agent 抽象，给出**纯架构设计**——模块划分、接口契约、数据流、时序图。
> **不包含**：任何 Java 代码、测试代码、SQL 模板、DDL 脚本。
> **目标读者**：智能体平台项目主程、Agent 框架下游对接方。
> **写代码前的最后一份文档**。

---

## 0. Context（为什么做这次架构设计）

- WISETao_custom_demo 是一个 xxl-job 调度的指标计算引擎，**没有任何 controller/query 层**，唯一的对外接口是 xxl-job admin。
- 已完成《通用智能问数设计方案 v1》(10 个 Tool) 与《智能体平台整合设计方案 v2》(14 个 Tool + Skill/Agent)，但都是**设计描述**，没有给出"代码怎么写"的架构骨架。
- 即将开发的智能体平台"灵知"要求 G3 阶段（W9-W11）交付"智能问数引擎 V1.0"，准确率 ≥ 85%、越权/DML 拦截率 100%、审计可还原。
- 本文档输出**架构骨架**，明确模块边界、调用契约、数据流，作为后续多团队并行实现的共同基线。

## 1. 设计目标与非目标

### 1.1 目标

1. **业务目标**：业务人员用自然语言提问，系统选择合适的 Tool 调用并合成答案。
2. **架构目标**：14 个 Tool 全部可独立实现、可独立替换、可独立测试；Tool 之间无相互依赖。
3. **安全目标**：所有时序/业务数据查询经校验层；写 SQL 100% 拦截；敏感表强制走预定义模板；全链路审计可还原。
4. **可观测目标**：每个 Tool 调用必带 `api/params/rowCount/executionMs/audit_id`；审计可完整还原一次问数。
5. **演进目标**：14 个 Tool 中已具备完整后端实现的（v1 的 10 个）优先落地；依赖外部服务（RAGFlow / 规则引擎 / KG）的 4 个 Tool（v2 新增）可以"先接口、后实现"。

### 1.2 非目标

- **不实现 LLM Provider 适配**：本架构假设 DSH（DeepSeek Harness）作为 LLM 调度层，本模块只提供 Tool 接口与 LLM 无关的 Backend 实现。
- **不实现 RAGFlow / Neo4j 后端**：这些是平台层依赖，本架构只定义访问契约与降级策略。
- **不实现前端 UI**：本模块只暴露 REST API；前端由前端组负责。
- **不实现 Skill/Agent 编辑端**：本模块只支持"运行态"调用 Skill/Agent；编辑态由 DSH Studio 负责。

**4 层划分**：

| 层 | 包名 | 职责 |
|---|---|---|
| **REST API 层** | `com.talent.query.api` | HTTP 入口、请求验证、响应包装、限流 |
| **编排层 (Orchestrator)** | `com.talent.query.core` | 加载元数据、调用 LLM、调度 Tool、调用校验/审计 |
| **Tool 层** | `com.talent.query.tool` | 17 个 ToolExecutor 接口 + 实现（14 个智能问数 + 2 个 AGP 业务 SQL + 1 个护栏，详见 §5 修订） |
| **数据访问层** | `com.talent.query.backend` | **5 类 Backend**：AGP 元数据库 / 项目业务库 / StarRocks 时序 / TSDB HTTP 网关 / 业务事实表 + 外部服务 |

> **关键原则**：层与层之间**只通过接口依赖**，从不直接 new 对方实现类。Spring 通过 `@Service` / `@Autowired` 注入。

## 4. 核心接口契约

### 4.1 `ToolExecutor`（所有 Tool 的统一接口）

```java
public interface ToolExecutor {
    String getName();                                              // "lookup_metric" / "aggregate" 等
    String getDescription();                                       // 给 LLM 看的人类可读描述
    JsonNode getParameterSchema();                                 // OpenAI function calling schema
    ToolResult execute(JsonNode params, ToolExecutionContext ctx)  // 主执行方法
        throws ToolExecutionException;
}
```

**核心约定**：
- 每个 Tool 一个 Spring `@Component`，由 `ToolRegistry` 自动扫描注入
- `getParameterSchema()` 返回 JSON Schema 字符串，供 LLM 调用时下发
- `execute()` 是纯函数（无状态），所有上下文从 `ToolExecutionContext` 拿
- 抛 `ToolExecutionException` 表示业务可重试错误（无权限、超阈值等）
- 抛 `RuntimeException` 表示系统级错误（DB 挂、网络断等），由 Orchestrator 兜底

### 4.2 `ToolExecutionContext`（Tool 执行上下文）

```java
public class ToolExecutionContext {
    String userId;              // 当前用户
    Long   appId;                // 多租户 appId
    String orgId;                // 用户所属组织（用于行级权限）
    List<String> userRoles;      // 用户角色（用于四级权限）
    String sessionId;            // 会话 ID（贯穿审计）
    Map<String, Object> sessionState;  // 会话内状态（多轮对话时使用）
    int  queryDepth;             // 递归深度（防止 Tool 嵌套调用死循环）
}
```

### 4.3 `ToolResult`（统一返回）

```java
public class ToolResult {
    boolean success;             // true=成功, false=失败
    String  toolName;            // 工具名
    String  apiOrSql;            // 调用的 SQL 或 HTTP URL（用于审计）
    JsonNode params;             // 实际参数
    JsonNode data;               // 业务数据（数组 / 对象）
    int     rowCount;
    long    executionMs;
    String  auditId;             // 审计 ID（写库后回填）
    Map<String, String> citations;  // 引用溯源 source_id / page / chunk_id
    String  errorMessage;        // 失败时填充
    String  errorCode;           // PERMISSION_DENIED / SENSITIVE_TABLE / DML_FORBIDDEN ...
}
```

### 4.4 `LLMClient`（LLM 抽象接口）

```java
public interface LLMClient {
    /** 调用 LLM 进行 Intent 抽取 + Tool 选择（带 system prompt + 工具 schema） */
    List<ToolCall> chatWithTools(String systemPrompt, String userMessage, List<ToolDefinition> tools);

    /** 调用 LLM 合成最终答案（无工具调用，纯生成） */
    String summarize(String systemPrompt, String userMessage, List<ToolResult> toolResults);
}
```

**实现策略**：
- `DSHLLMClient`：v2 默认，对接 DeepSeek Harness（OpenAI 兼容协议 + tool calling）
- `DirectLLMClient`：v1 默认（不接 LLM 时用 mock），返回固定的空 Intent
- v1 阶段只实现 `DirectLLMClient`（返回空 + 走 `/by-intent` 端点手动测试）

### 4.5 `ValidationLayer`（校验层）

```java
public interface ValidationLayer {
    /** 检查 SQL 是否允许执行（白名单 + 禁 DML + 敏感表 + 字段权限 + 行级权限注入） */
    ValidatedSql validateSql(String sql, ToolExecutionContext ctx) throws ValidationException;

    /** 检查 Tool 调用是否允许（按 toolId + userId + appId） */
    void validateToolCall(String toolId, ToolExecutionContext ctx) throws ValidationException;

    /** 校验 facts（用于 evaluate_rules） */
    ValidatedFacts validateFacts(JsonNode facts, ToolExecutionContext ctx);
}
```

**`ValidatedSql`** 返回值：

```java
public class ValidatedSql {
    boolean allowed;             // true=放行, false=拒绝
    String  reason;              // 拒绝原因
    String  rewrittenSql;        // 注入行级权限后的最终 SQL
    String  sensitiveReason;     // 如果敏感表，给出替代 Tool 名
    String  replacementTool;     // 替代 Tool
}
```

### 4.6 `AuditService`（审计）

```java
public interface AuditService {
    /** 写入一条审计记录（哈希链 + 仅追加） */
    String writeAudit(AuditEntry entry);

    /** 查询审计（管理端用） */
    List<AuditEntry> queryAudit(AuditQuery query);

    /** 验证哈希链完整性（管理端用） */
    boolean verifyChain(Long startAuditId, Long endAuditId);
}
```

### 4.7 `Backend`（数据访问抽象）

```java
public interface Backend {
    /** 执行 SQL（已被 ValidationLayer 校验通过） */
    QueryResult executeSql(String sql, Object[] params, QueryOptions opts);

    /** HTTP GET 调用 */
    HttpResult httpGet(String url, Map<String, String> headers, Map<String, String> params);

    /** HTTP POST 调用 */
    HttpResult httpPost(String url, Map<String, String> headers, JsonNode body);
}
```

**实现**：
- `StarRocksBackend`：基于 `timeDataSource` 注入的 `JdbcTemplate`
- `RAGFlowBackend`：基于 `RestTemplate` 或 `OkHttpClient`（待选）
- `RulesEngineBackend`：HTTP 客户端
- `KGBackend`：HTTP 或 JDBC（取决于 KG 后端选型）

**每个 Tool 的契约相同**：
- 实现 `ToolExecutor` 接口
- 包名约定：`com.talent.query.tool.{类别}`
- Spring `@Component("tool_<name>")` 注册，由 `ToolRegistry` 自动发现
- 参数/返回都通过 `JsonNode` 或具体 POJO（POJO 由 Jackson 自动转换）

**5 类数据来源（按调用频率）**：
1. **AGP 元数据库**（★漏掉）→ `execute_sql_agp_meta` → 人员/组织/设备基础模型
2. **项目业务数据库**（★漏掉）→ `execute_sql_business` → 工单/告警/订单/业务流水
3. **TSDB 时序数据库** → `latest_value/time_series/aggregate/business_metrics` → WT_DATA + WT_TAG + 字典
4. **TSDB HTTP 网关** → `wide_history/aggregate_http` → 差值电量 + 18 高级算子
5. **业务事实表 + 外部服务**（v2）→ `business_metrics/search_knowledge/query_kg/evaluate_rules`

## 7. 校验层（安全核心）的规则模型

```
                          ┌─────────────────┐
                          │  LLM 生成的 SQL  │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 1. 解析/正则匹配  │
                          │    SELECT 开头   │
                          │    非 DML/DDL    │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 2. 提取表名      │
                          │    FROM 后的列表 │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 3. 敏感表检查     │
                          │    WT_SENSITIVE_ │
                          │    TABLES       │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 4. 白名单检查     │
                          │    application. │
                          │    yml 配置     │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 5. 字段权限检查   │
                          │    WT_FIELD_     │
                          │    PERMISSION   │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 6. 行级权限注入   │
                          │    追加 AND      │
                          │    org_id IN (?) │
                          └────────┬────────┘
                                   │
                          ┌────────▼────────┐
                          │ 7. 只读账号执行   │
                          │    Backend.       │
                          │    executeSql()  │
                          └─────────────────┘
```

**关键决策**：
- 校验层**只接受 LLM 生成的 SQL**，不允许 LLM 直接调用 Backend.executeSql()
- 校验失败抛 `ValidationException`，Orchestrator 捕获后写入审计并返回拒绝原因
- 敏感表命中 → 拒绝 + 返回 `replacement_tool` 提示（让 LLM 改用预定义模板）
- **行级权限的注入是必须的**——即使 SQL 合法，也要在 WHERE 子句里追加 org 过滤

## 9. Skill / Agent 抽象（v2 增量）

### 9.1 Skill 定义

```java
public class SkillDefinition {
    String id;                  // "intelligent-query" / "water-dispatch"
    String name;                // "智能问数" / "防洪调度"
    String description;         // 给 LLM 看
    String triggerDesc;         // 触发条件（自然语言）
    List<String> toolIds;       // 包含的 Tool 列表
    String promptTemplate;      // Skill 专属 system prompt
    boolean enabled;
}

public class SkillRegistry {
    SkillDefinition get(String skillId);
    List<SkillDefinition> findByTriggerDesc(String query);  // 模糊匹配
}
```

**Skill vs Tool 的关系**：
- **Tool**：原子能力，调用 1 个后端（如 `aggregate` → 1 条 SQL）
- **Skill**：场景化能力包，封装多个 Tool + 触发条件 + 提示词模板（如 `intelligent-query` Skill → 包含 lookup_* + aggregate + wide_history + business_metrics）

### 9.2 Agent 定义（v2，骨架占位）

```java
public class AgentDefinition {
    String id;
    String name;
    String persona;              // 角色人设
    List<String> skillIds;
    List<String> subAgentIds;    // 子 Agent
    boolean enabled;
}
```

**架构决策**：Agent 编排由 DSH 负责，**本模块不实现 Agent 运行时**，只提供：
- `AgentDefinition` / `SkillDefinition` 数据模型
- `SkillExecutor`（Tool 14）作为 Skill → Tool 的桥接
- 数据存储：`WT_AGENT_REGISTRY` / `WT_SKILL_REGISTRY` 表

### 9.3 SkillExecutor 流程

```
LLM 调用 skill(skill_id="intelligent-query", inputs={question, time_range, ...})
     │
     ▼
SkillExecutor.execute()
     │
     ├── 1. SkillRegistry.get(skillId) → SkillDefinition
     │
     ├── 2. 用 promptTemplate 渲染 system prompt
     │
     ├── 3. 把 skill.toolIds 转成 Tool 列表
     │
     ├── 4. 调用 LLMClient.chatWithTools(renderedPrompt, inputs, tools)
     │
     ├── 5. 收到 List<ToolCall> 后：
     │     - 对每个 ToolCall 调 ToolRegistry.execute()
     │     - 走完整校验+审计流程
     │
     └── 6. 聚合所有 ToolResult → SkillResult 返回
```

## 12. 关键决策记录（ADR 摘要）

| 决策 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 包命名空间 | `com.talent.query.*` | `com.talent.intelligentquery.*` | 与 `com.talent.job.*`、`com.talent.server.*` 平级 |
| 层数 | 4 层（API / Core / Tool / Backend）| 3 层 / 5 层 | 4 层刚好切分职责；多加会冗余 |
| 14 Tool 的依赖方向 | Tool → Backend（向下）| Tool → 多个类（散弹）| 单一后端依赖，便于替换与 mock |
| LLM 抽象 | `LLMClient` 接口 + DSH 实现 | 直接硬编码 DSH | 留出 Mock 实现，便于 v1 阶段不接 LLM |
| 校验层位置 | Tool 内部 → 调用前 | Tool 内部 → 调用中 | 早失败，省 DB 调用 |
| 审计写入 | 业务调用前同步写 | 异步队列 | 审计失败业务回滚，符合"零外传"红线 |
| 字典表持久化 | StarRocks 同库 | MySQL 独立库 | 与数据同库便于 JOIN；权限统一 |
| Tool 注册方式 | Spring `@Component` 自动扫描 | 手工 Map 注册 | 利用 Spring IoC，少写代码 |
| 14 Tool 不全部实现 | 接口完整 + 占位实现 | 全量真实实现 | 让接口契约先稳定，后端可逐步替换 |
| 时序数据时间字段 | `timestamp` (DATETIME) | `ts` | 与现有 WT_DATA DDL 一致 |
| 业务字典表命名 | `WT_METRIC_DICT` / `WT_DEVICE_DIM` | `metric_dict` / `device_dim` | 与 AGP 现有 WT_ 前缀约定一致 |
| 时区 | 系统默认时区 | 显式 UTC | 兼容现有 SQL（多数用 `LOCAL TIME`）|

## 15. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| WT_METRIC_DICT / WT_DEVICE_DIM 表不存在 | lookup_* Tool 报空 | 占位实现：返回空列表 + 警告日志；后续迁移真实字典 |
| timeDataSource 指向的 StarRocks 不可达 | 所有 SQL Tool 失败 | Backend 抛 `BackendException`，Orchestrator 兜底返回 "数据源暂不可用" |
| LLM Provider 未配置 | /ask 端点 503 | v1 阶段只实现 /by-intent；/ask 路由可存在但调用 DirectLLMClient 占位 |
| 校验层误拦截合法查询 | 用户体验差 | 配置 `whitelist-overrides` 在 application.yml；DEBUG 模式打印拦截原因 |
| 审计哈希链断裂（数据被外部改）| 审计失效 | 写入前 LOCK TABLE；定期 backup `WT_QUERY_AUDIT` 到 DFS |
| Tool 并发调用导致 LLM Token 超限 | 性能问题 | Orchestrator 串行调用；并发上限 = 单 LLM 端点 TPS |
| 时区不一致导致时序查询错位 | 数据错误 | `SystemMetadata.timezone` 强制注入到所有 Tool，Backend 内部统一转 UTC |
